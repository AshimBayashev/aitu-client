# Aitu здорового человека

Неофициальный клиент [Aitu](https://aitu.io) для Windows. Веб-версия долго отправляет сообщения, не даёт разложить чаты по папкам, персонализировать вид чатов, присутствует много багов и неудобств. Этот клиент оставляет обычную переписку и даёт настроить вид под себя.

ВАЖНО! Проект не связан с BTS Digital. Вход идёт в ваш собственный аккаунт через окно Passport.

Установить для Windows можно из Microsoft Store: [Aitu здорового человека](https://apps.microsoft.com/detail/9ND7DC3NGZ6F?hl=ru-ru&gl=KZ).

## Функционал

- Список чатов, история и отправка текста
- Файлы, ссылки в сообщениях и фото профилей
- Эмодзи и голосовые: запись из поля ввода и прослушивание прямо в чате
- Ответы на сообщения и карточка чата справа
- Закреплённые чаты без ограничения по количеству
- Сообщения одного человека собираются в пачку
- Галочки доставки и прочтения
- Папки в духе Telegram: «Все», «Личные», «Группы», «Каналы» и свои
- Светлая и тёмная тема, свой цвет акцента, шрифт, размер, плотность списка и фон чата
- Уведомления о новых сообщениях
- Закрытие окна прячет клиент в трей, полный выход — из меню трея

Папки, закрепления и оформление остаются на этом компьютере. Переписка подтягивается из аккаунта Aitu.

## Запуск

Нужны Windows 10 или 11, WebView2, Node.js 20 и Rust со сборкой MSVC (Visual Studio Build Tools).

```bash
npm install --legacy-peer-deps
npm run tauri dev
```

Установщик:

```bash
npm run tauri build
```

## Как устроено

Клиент — процесс Tauri 2. Окно рисует WebView2 со страницей React. Сеть, сессия и разбор протокола живут в Rust (`src-tauri/src/aitu.rs`, `proto.rs`). Страница вызывает команды через `invoke` и получает уже разобранные структуры. Обратно Rust шлёт события `aitu-session`, `aitu-login-error`, `aitu-login-closed` и `aitu-open-chat`.

Команды: `session_status`, `begin_login`, `logout`, `list_dialogs`, `list_history`, `send_message`, `send_voice`, `open_attachment`, `mark_read`, `set_active_chat`. Аргументы в JavaScript в camelCase, в Rust — snake_case, serde переименовывает их сам. Capabilities разрешают `invoke` только окну `main`. Окно Passport в этот список не входит и команды процесса вызвать не может.

### Два хранилища

Состояние аккаунта держит `AituState` в памяти процесса: cookie, `installation_id`, `user_id`, имя, идентификатор активного чата и общий клиент reqwest. На диск это пишется в `session.json` в каталоге данных приложения. `installation_id` — UUID, создаётся один раз и уходит в Aitu как идентификатор устройства. `logout` обнуляет cookie, пользователя, имя и активный чат и перезаписывает файл. Каталог данных определяется идентификатором Tauri `local.aitu.client`, поэтому сессия переживает пересборку с тем же идентификатором.

Состояние этого компьютера лежит в `localStorage` под ключом `aitu-client-v1`: настройки, папки, кэш сообщений, непрочитанные, недавние эмодзи и порядок закреплений. Перед записью из файлов вырезается `localUrl`, чтобы в хранилище не оседали временные blob-адреса. В десктопном режиме стартовые чаты и история пустые, соединение в состоянии `checking`. Фикстуры из `data.ts` подставляются только когда страница открыта без Tauri.

Папки и закрепления сервер не хранит. Встроенные папки пересобираются при каждом списке диалогов из `kind` чата: `GROUP` и `DISCUSSION` попадают в группы, `CHANNEL` в каналы, остальные в личные. Своя папка — это имя и явный список идентификаторов. Идентификатор, которого больше нет в списке диалогов, из неё выпадает. Закрепления — упорядоченный массив идентификаторов. `null` означает, что пользователь порядок ещё не задавал. Пустой массив означает, что закреплений нет. При сборке списка закреплённые идут по индексу этого массива, остальные — по `lastAt`. Выход из аккаунта `localStorage` не чистит.

### HTTP-клиент

reqwest собран с таймаутом 25 секунд, `http1_only`, `no_proxy` и `User-Agent: AituDesktop/0.1`. Пустой User-Agent `api.aitu.io` отвечает 500. На grpc-запросы добавляются `Cookie`, `X-Application: Aitu`, `X-App-Locale: ru` и `X-Device-Id` с `installation_id`. Значение заголовка проходит через `HeaderValue::from_str`, поэтому перевод строки в cookie запрос обрывает.

### Вход

`begin_login` делает Twirp JSON `POST /twirp/kz.btsd.messenger.auth.AuthService/GetPassportOAuthUrl` с телом `{ url, installation_id }` и открывает полученный адрес во втором webview с меткой `aitu-login`. Подписка на `PageLoadEvent::Finished` срабатывает, когда хост страницы равен `aitu.io` или `www.aitu.io`. Сбор cookie вынесен в отдельный поток: на Windows `cookies_for_url` с UI-потока вешает окно. Cookie читаются для `https://api.aitu.io/`, `https://aitu.io/` и `https://passport.aitu.io/`, склеиваются в одну строку `name=value` и проверяются вызовом `UserService/GetMe`. Проверка делается дважды, между попытками 600 мс. После успешного `GetMe` cookie, id и имя пишутся в `AituState` и в `session.json`, в страницу уходит `aitu-session`, выставляется `login_done`, окно входа закрывается.

Если окно входа уничтожено без `login_done`, страница получает `aitu-login-closed`. `session_status` при старте снова вызывает `GetMe`. Ошибка этого вызова стирает cookie и возвращает состояние «не вошли», а не ошибку команды.

### Два протокола на одном хосте

Профиль и OAuth — Twirp JSON по `/twirp/...` на `https://api.aitu.io`.

Диалоги, история, отправка, ответ и отметка прочитанного — grpc-web-text на том же хосте, уже без `/twirp`:

- `DialogService/GetDialogs` — пустое тело
- `MessageService/GetHistory` — peer и лимит 40
- `MessageService/SendMessage`, для канала `SendChannelMessage`
- `MessageService/ReplyMessage`, если задан `replyTo`
- `MessageService/MessageReadCommand`

Запрос собирается так: байт флага `0`, длина protobuf как `u32` big-endian, сами байты, затем весь кадр в standard base64. Заголовки `Content-Type` и `Accept` — `application/grpc-web-text`, плюс `X-Grpc-Web: 1`. Ответ приходит несколькими кадрами, каждый в своём base64. Знак `=` стоит в конце кадра, поэтому строку ответа нельзя декодировать целиком: декодер режет её по паддингу. Из бинарных кадров отделяются данные и grpc-трейлеры. `grpc-status`, отличный от `0`, и HTTP 401 становятся ошибкой команды. 401 на стороне страницы означает, что сессию надо получить заново.

Полной схемы protobuf в репозитории нет. `proto.rs` сам читает varint и length-delimited поля и интерпретирует только номера, снятые с официального веб-клиента. Неизвестные поля пропускаются.

`PeerType`: `USER` 0, `GROUP` 1, `CHANNEL` 2, `BOT` 3, `DISCUSSION` 4, `APP` 5, `BUSINESS_CHAT` 6. В модель страницы это сворачивается в `kind`: группа, канал или `direct`. Для канала `encode_send` кладёт в поле 1 не peer, а сообщение с id канала. Исходящее сообщение определяется сравнением `sender_id` с `user_id` из сессии. Имя автора подставляется только у входящих в `GROUP` и `DISCUSSION`. История приносит сообщения в поле 2, пользователей в поле 3, ботов в поле 5 и сообщения-источники цитат в поле 6. Цитата собирается по `replyToMessageId` из этого индекса.

Статус доставки лежит во внутреннем теле (`DataMessage`, `ChannelMessage` или `BusinessChatMessage`), поле 2: `PENDING` 0, `SENT` 1, `READ` 2. Внешнее поле 2 сообщения — это время. В модель страницы значение 2 переводится в `read`, любое другое известное значение и отсутствие поля — в `sent`. Локальные состояния `sending` и `failed` сервер не присылает: их ставит страница до ответа команды и после её ошибки.

Медиа внутри сообщения разбирается по номеру поля: 11 файл, 12 изображение, 13 видео, 14 аудио, 16 стикер, 17 музыка, 18 gif. Служебное тело, звонок и неразобранное вложение заменяются короткими текстовыми метками и в ленту как сырой protobuf не попадают.

### Синхронизация

Постоянного потока от сервера нет. Списки обновляются опросом.

Страница раз в 12 секунд вызывает `list_dialogs` и раз в 5 секунд — `list_history` открытого peer. Перед применением результата она спрашивает у окна `isVisible`, `isFocused` и `isMinimized`. Непрочитанное активного чата обнуляется и `mark_read` уходит только когда окно видно, в фокусе, не свёрнуто и `document.visibilityState` не `hidden`. У WebView2 `visibilityState` страницы при свёрнутом окне Windows остаётся `visible`, поэтому проверки окна недостаточно заменить проверкой страницы. Раз в секунду, на `visibilitychange` и на `onFocusChanged` состояние перечитывается. Переход из «окно не перед глазами» в «перед глазами» дочитывает активный чат.

Отдельный `std::thread` в Rust раз в 12 секунд сам вызывает `GetDialogs` через `block_on`. Таймер страницы для этого не годится: скрытый WebView останавливает JavaScript. Первый успешный снимок только запоминает счётчики. Следующие сравниваются с ним. Тост создаётся, когда непрочитанное чата выросло. Чат, записанный в `active_chat` и открытый в видимом несвернутом окне с фокусом, пропускается. Текст тоста — превью до 140 символов или строка «Новое сообщение». В extra кладётся `chatId`. Обработчик действия тоста поднимает окно `main` и эмитит `aitu-open-chat`. Ошибка опроса прошлый снимок не стирает. Ответ «не вошли» снимок сбрасывает, чтобы следующий успешный список снова стал базовой линией.

### Отправка и слияние

Перед `invoke` страница вставляет локальное сообщение со статусом `sending` и собственным `localId`. `send_message` сначала загружает каждый путь multipart-полем `file` на `https://media-upload.api.aitu.io/api/v1/media/uploadfile` (потолок 200 МБ, запрос с cookie), затем шлёт `SendMessage` или `SendChannelMessage`. Если `replyTo` непустой, метод меняется на `ReplyMessage`: поле 1 — id исходного сообщения, поле 2 — вложенная команда отправки.

Когда приходит история, `mergeMessages` оставляет локальные `sending` и `failed`, для которых на сервере ещё нет исходящего с тем же текстом, теми же именами файлов и разницей `sentAt` меньше 120 секунд. Совпавшие локальные копии выбрасываются, остаётся серверная запись со статусом `sent` или `read`.

### Медиа

Скачивание аватара и файла — публичный GET `https://media-cdn.aitu.io/api/v2/media/download/{avatar|file}/{id}`. Cookie на этот хост не отправляется. В `file_id` маленького аватара бывает `?`. Кодируется только путь до вопроса, исходный query дописывается как есть.

`open_attachment` проверяет id (длина 8–80, только буквы, цифры, `-` и `_`), кладёт байты в `app_cache_dir/media/{id}/{name}` и открывает путь через `opener`. Повторный вызов с тем же id файл заново не качает.

### Голосовые

Отдельного метода голосового сообщения в API нет. Страница пишет микрофон через `MediaRecorder`, декодирует blob в `AudioContext`, сводит каналы в моно, линейно передискретизирует в 22050 Гц и собирает PCM 16-bit little-endian WAV с заголовком RIFF. Длительность ограничена 3 минутами, записи короче 400 мс отбрасываются. Байты уходят в `send_voice` как base64. Rust принимает `audio/wav`, `webm`, `ogg`, `mp4`/`m4a`/`aac` и `mpeg`, отвергает прочие MIME и тела больше 16 МБ, грузит байты с именем `voice.wav` и `kind = 3`.

В истории тот же объект возвращается обычным файлом: protobuf-поле 11, имя `voice.wav`. Разбор по имени `voice.(wav|webm|ogg|m4a|mp3)` переписывает kind в `audio` и превью в «Голосовое сообщение». Воспроизведение идёт из `localUrl` или с CDN через элемент `audio`. В `open_attachment` такие файлы не передаются.

### Окно и трей

`CloseRequested` окна `main` вызывает `prevent_close` и `hide`, пока атомик `QUITTING` выключен. Трей создаётся в `setup`: пункты «Открыть» и «Выход», левый щелчок и двойной щелчок делают `unminimize`, `show`, `set_focus`. «Выход» ставит `QUITTING` и вызывает `app.exit(0)`, и только тогда закрытие окна процесс завершает.

### Сборка

`npm run tauri build -- --bundles nsis` даёт установщик. Язык мастера задан как `Russian`. Сборка MSI на этом имени продукта останавливается: WiX не кладёт кириллицу в кодовую страницу 1252. Пакет Microsoft Store — отдельный MSIX поверх того же бинарника (`store/pack.ps1`), установщик NSIS магазин не принимает. Universal-сборку macOS делает workflow `macos.yml` по `workflow_dispatch`. Подписи Apple у `.dmg` нет.
